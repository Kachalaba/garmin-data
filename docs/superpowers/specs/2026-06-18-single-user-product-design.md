# Garmin Data: завершённый личный продукт

## Назначение

Проект является локальным инструментом одного пользователя. Он должен самостоятельно
забирать данные Garmin, рассчитывать персональные сигналы восстановления, проверять
качество данных, сохранять понятный ежедневный отчёт и оставаться полезным при сбоях
сети. Внешние сервисы не должны быть обязательны для получения результата.

## Продуктовый результат

Основной сценарий — одна команда:

```bash
python3 -m garmin_health daily
```

Она последовательно:

1. создаёт безопасную резервную копию текущей SQLite-базы;
2. пытается синхронизировать последние два дня Garmin;
3. запускает все локальные analytics-модули независимо друг от друга;
4. проверяет свежесть и полноту ключевых данных;
5. формирует детерминированный Markdown-отчёт без LLM;
6. сохраняет отчёт в `reports/YYYY-MM-DD.md` и обновляет `reports/latest.md`;
7. записывает итог запуска и ошибки в служебную таблицу и лог;
8. возвращает ненулевой exit code только когда локальный результат непригоден.

Если Garmin недоступен, pipeline продолжает работу на последнем пригодном снимке базы,
явно помечая устаревшие данные. Notion и Claude остаются дополнительными способами
интерпретации и публикации, но не входят в обязательный путь.

## Пользовательский интерфейс

Пакет `garmin_health` предоставляет единый CLI:

- `daily` — полный ежедневный цикл;
- `report [--date YYYY-MM-DD]` — пересоздать отчёт без сетевой синхронизации;
- `healthcheck [--json]` — показать свежесть, пропуски, состояние аналитики и БД;
- `backup [--keep N]` — создать проверенную резервную копию и удалить старые;
- `analytics` — запустить локальные расчёты без Garmin sync.

Существующие команды `garmy_sync.py` и `python -m analytics.run_all` сохраняются для
совместимости и диагностики.

## Архитектура

### `garmin_health/config.py`

Единая конфигурация путей и параметров из env. Конфигурация вычисляется при вызове,
а не фиксируется навсегда во время импорта, чтобы CLI и тесты могли безопасно работать
с временными базами.

### `garmin_health/database.py`

Подключение SQLite с `busy_timeout`, проверкой целостности и безопасным backup API.
Служебная схема содержит таблицу `pipeline_runs`, не изменяя таблицы библиотеки
`garmy`. Сложная система миграций для личного продукта не нужна: additive-only DDL
остаётся идемпотентным.

### `garmin_health/healthcheck.py`

Возвращает структурированный результат, а форматирование для терминала и JSON отделено
от проверки. Проверяются:

- существование и `PRAGMA quick_check` базы;
- последняя дата `daily_health_metrics`;
- наличие сна, HRV и resting HR за последние семь завершённых дней;
- последние даты таблиц `hrv_baseline`, `rhr_anomaly`, `risk_scores`,
  `activity_weather` и `workout_intervals`;
- результат последнего полного pipeline-запуска.

Отсутствие опциональной таблицы не ломает проверку: оно отображается как предупреждение.

### `garmin_health/report.py`

Генерирует Markdown из данных SQLite. Отчёт содержит дату данных, общий статус,
readiness, сон, HRV, resting HR, доступные risk signals, качество данных и конкретную
осторожную рекомендацию по нагрузке. Формулировки не называют score диагнозом или
вероятностью заболевания. Если данных мало, отчёт честно сообщает это вместо
догадок.

### `garmin_health/pipeline.py`

Оркестратор с внедряемыми функциями sync и analytics. Это позволяет тестировать
порядок, частичные сбои и exit codes без Garmin API. Ошибка sync становится
предупреждением, если healthcheck подтверждает пригодный локальный снимок. Ошибка
генерации отчёта, повреждённая база или отсутствие ключевых данных являются ошибкой.

### `garmin_health/cli.py` и `garmin_health/__main__.py`

Тонкий argparse-интерфейс без дополнительного CLI-фреймворка. Вывод ориентирован на
одного пользователя и launchd: короткий итог в stdout, подробности в rotating log.

## Надёжность данных

- Backup создаётся через SQLite backup API, а не копированием открытого файла.
- После создания backup выполняется `PRAGMA quick_check`.
- Хранятся последние семь ежедневных копий; директории базы и отчётов исключены из git.
- Каждый pipeline run получает состояние `running`, затем `success`, `partial` или
  `failed`, временные метки и краткую ошибку.
- Одновременные локальные запуски сериализуются advisory lock-файлом.
- Логи сохраняют все уровни в rotating-файл; `WARNING+` дополнительно выводится в
  stderr.

## Аналитические ограничения

`risk_scores` остаётся набором персональных эвристических сигналов. В коде и
документации `illness_risk_score` описывается как индикатор отклонения, а не как
клиническая вероятность. Проект не ставит диагноз и не заменяет медицинскую помощь.
Исторические формулы не расширяются новой моделью: для одного пользователя важнее
прозрачность и стабильность текущих вычислений.

## Зависимости и установка

Runtime-зависимости остаются в `requirements.txt`; инструменты разработки выносятся в
`requirements-dev.txt`. `pyproject.toml` хранит единые настройки pytest, Black и
isort. Установка остаётся обычным virtualenv без упаковки и публикации в PyPI.

## Тестирование

Тесты используют временные SQLite-базы и проверяют:

- поиск пропусков и объединение дат в диапазоны;
- конфигурацию logging и сохранение warning/error в файл;
- backup, retention и integrity check;
- healthcheck на свежих, устаревших и неполных данных;
- генерацию полного и degraded Markdown-отчёта;
- pipeline при успехе, сетевом сбое и непригодной базе;
- ключевые граничные случаи HRV, RHR и risk-score helpers.

CI на Python 3.11 запускает pytest, Black, isort, flake8, compile-check и проверку
Grafana JSON/YAML.

## Документация и автоматизация

README описывает один рекомендуемый ежедневный путь и отделяет обязательные локальные
функции от опциональных Claude/Notion/Grafana. `docs/setup.md` содержит готовый launchd
пример для `python -m garmin_health daily`, проверку ручного запуска и восстановление
из backup. Старые упоминания числа analytics-модулей, `sync.log` и состава зависимостей
приводятся в соответствие с кодом.

## Вне scope

- многопользовательский режим, аккаунты и роли;
- публичный API или постоянно работающий web-сервер;
- мобильное приложение;
- собственная LLM-интеграция и обязательная публикация в Notion;
- облачная база и сложная система миграций;
- автоматические медицинские решения.

## Критерии готовности

Работа завершена, когда:

1. все пять CLI-команд работают на временной и реальной локальной базе;
2. `daily` создаёт backup, запускает pipeline и сохраняет пригодный отчёт;
3. сетевой сбой не уничтожает локальный результат и отражается как partial run;
4. повреждённая или пустая база даёт понятную ошибку и ненулевой код;
5. CI действительно запускает весь набор проверок;
6. документация воспроизводит установку и ежедневный запуск;
7. все тесты и статические проверки проходят в чистом Python 3.11 environment;
8. существующие пользовательские данные и внешние Garmin-таблицы не повреждены.
